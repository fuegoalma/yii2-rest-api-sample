# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Yii2 (basic template) REST API for users, albums, and photos. PHP 8.5, MySQL 8, everything runs inside Docker (Compose **v2** — invoke it as `docker compose`, with a space, not the legacy `docker-compose`) — all PHP/console commands must be executed through `docker compose exec web` (use the `Makefile` shortcuts below, e.g. `make test` instead of typing the full command). The environment is defined by a single multi-stage `Dockerfile` (`base` → `dev` → `prod`); the **Imagick** extension (used for photo uploads) plus `pdo_mysql`/`mysqli`/`pcntl` (the queue worker's graceful shutdown) and Composer are baked into the `base` stage. `docker-compose.yml` builds the `dev` stage (`target: dev`) and bind-mounts the project directory, so `composer install` and the code live on the host and container startup is instant; the CD pipeline builds the self-contained `prod` stage. Keep the `Dockerfile`'s `base` stage as the single source of truth for the runtime — don't reintroduce runtime extension installs in compose. Alongside `web` there is a **`cron`** service that reuses the same image (shared `image: yii-app:dev` name → built once) but runs the cron daemon instead of Apache: its entrypoint (`docker/cron/entrypoint.sh`) snapshots the container env into `/etc/container-env` (cron jobs run with a bare environment) and installs the versioned schedule `docker/cron/crontab` into `/etc/cron.d/app-cron`. That crontab is the single place to declare scheduled console commands — currently a daily `refresh-token/prune`; each line sources the env and logs to the container stdout (`docker compose logs cron`). There is also a **`worker`** service (same shared image) whose entrypoint is the long-running queue worker `yii queue/listen` instead of Apache/cron, with `restart: unless-stopped` — see **Background jobs (queue)**. `make rebuild` builds the image and (re)starts `web`, `cron` and `worker`.

## Codebase Navigation (CodeGraph) and rtk — mandatory tooling

**CodeGraph must always be tried first — it is not one option among several.** Before running `ls`, `cat`, `grep`, `find`, opening a directory listing, or reading a whole file to answer a code-navigation question, try the matching `codegraph` command from the list below. Drop to `ls`/`cat`/`grep`/`find`/raw shell **only** when CodeGraph genuinely cannot do the job — the index is stale and `codegraph sync` doesn't fix it, the operation has no CodeGraph equivalent (e.g. listing a plain directory, viewing a non-code file like a `.env`/YAML/Markdown file, or reading the specific file you already located through CodeGraph). Never reach for the direct tool first "to be safe" or "to double-check" — that defeats the token savings CodeGraph exists for; only fall back once CodeGraph has actually been tried and fell short.

This repo has a [CodeGraph](https://github.com/colbymchenry/codegraph) index (`.codegraph/`, local-only, gitignored). It answers "where is X" / "who calls X" / "what does X touch" directly from the index instead of spending tokens scanning file contents:

- `codegraph query "<name>"` — find a symbol (class/method/interface/file) by name.
- `codegraph explore "<question>"` — relevant symbols' source + call paths for an area, in one shot (e.g. `codegraph explore "how are refresh tokens rotated"`).
- `codegraph node <name>` — one symbol's source plus its callers/callees.
- `codegraph callers <symbol>` / `codegraph callees <symbol>` — who calls a method / what it calls.
- `codegraph impact <symbol>` — what else would be affected by changing a symbol (use before refactoring a shared class like `BaseCrudService`, `ApiController`, or a contract in `models/contract/`).
- `codegraph affected <files...>` — which test files cover a set of changed source files.

Run `codegraph sync` after a batch of edits (or `codegraph status` to check if the index is stale) so later lookups reflect the current code. Still use `Read`/`Edit` for the actual file content once CodeGraph has told you where to look — CodeGraph replaces the *searching*, not the reading. When CodeGraph can't help (config/YAML/Markdown files, `.env`, directory listings, log/output files), `ls`, `cat`, `grep`, `find` and other plain commands are fine — the mandate is "CodeGraph first", not "CodeGraph only".

**rtk** (Rust Token Killer, see `~/.claude/RTK.md`) is the token-optimized proxy for everyday dev/CLI operations (git, etc.) — a Claude Code hook transparently rewrites commands (e.g. `git status` → `rtk git status`) so it's used by default at zero extra effort, but meta commands (`rtk gain`, `rtk gain --history`, `rtk discover`, `rtk proxy <cmd>`) must be invoked directly. Only fall back to the raw/unfiltered command (`rtk proxy <cmd>`, or bypassing rtk entirely) when rtk can't handle the case — don't do it as a default habit.

**All code MUST follow SOLID, DRY, and KISS.** Non-negotiable for every change: no duplicated logic (extract shared code into base classes/traits/helpers, including tests), depend on interfaces from `models/contract/` rather than concretions, keep each class to a single responsibility, and prefer the simplest design that works — don't add abstractions for hypothetical future needs. When touching existing code that violates these principles, fix the violation rather than extending it.

## Test-Driven Development — mandatory

**This project is TDD. No production code changes without a test that failed first, in the same change.** Write the test, watch it fail for the right reason, then write the least code that makes it pass, then refactor. A test authored after the code — or one that has never been seen red — has not been shown to test anything, so write it first even when the implementation feels obvious.

**The suite must stay at 100% line coverage** of `commands/`, `components/`, `controllers/` and `models/` (scope declared in `codeception.yml`; `config/`, `migrations/`, `web/`, `tests/` and the interfaces in `models/contract/` are excluded — a file with no executable lines is 0/0 and neutral). `make coverage` runs the suite with coverage and enforces the gate through `tests/bin/coverage-check.php`, which prints every file under 100% with its uncovered line numbers. **Run it before calling any task done** — CI runs the same gate and goes red below 100%.

Non-negotiable rules for keeping that honest:

- **`@codeCoverageIgnore` requires a written justification** in a comment saying why the code is unreachable *by construction*. "Hard to test" is not unreachable. Two examples in the tree show the bar: `RefreshTokenRepository::revoke()` (a `save(false)` that cannot return false without a `beforeSave` hook) and `RolesController::accessResource()` (required by the abstract base, never consulted because both access hooks are overridden). Reaching for the annotation more than rarely means the design needs a seam, not an exemption — see `StopSignalInterface`, extracted precisely so the worker's infinite loop became testable.
- **Never add `@covers` / `#[CoversClass]`.** Codeception's test wrapper implements `StrictCoverage`, so such an annotation narrows what the test is credited with covering and silently lowers the total without erroring.
- **Both suites must run in ONE `codecept run`.** Coverage is merged across suites at the end of the run, so `codecept run unit` followed by `codecept run functional` makes the second report overwrite the first. This is why `make coverage` has no per-suite variant.
- **Don't duplicate test infrastructure.** Shared unit helpers belong on `tests/_support/BaseUnitTest.php`, shared functional ones on `tests/_support/BaseCest.php` — the DRY mandate above applies to tests as much as to production code.
- **Prefer a real integration test where the integration *is* the behaviour.** Repositories, ActiveRecord models and the seeder are covered by exercising them against the test database (see `SeederCest`, `RbacAssignCest`), not by asserting on mocked queries.
- **When code turns out to be unreachable because nothing uses it, delete it** rather than testing or ignoring it — that is the KISS/YAGNI mandate above, and it is how `Album::extraFields()` (dead since `AlbumsController::actionView` moved to a DTO) and a since-removed `deleteDir()` on the photo storage class were dropped once coverage showed they had no callers. The same rule retired `ImagickFactoryInterface`: an abstraction whose only implementation nothing ever substituted is not a seam, it is a file.

pcov is baked into the Dockerfile `base` stage but **disabled by default** (`pcov.enabled=0`), so `make test`/`make test-one` — the inner loop — pay nothing; only `make coverage` enables it for that process. CI installs its own pcov via `shivammathur/setup-php` (`coverage: pcov`); the two are independent, so a change to one needs the same change to the other.

## Commands

**Whenever a `Makefile` target exists for what you're about to run, use `make <target>` — never type out the underlying `docker compose ...`/`docker compose exec web ...` command by hand,** even for a one-off or "just this once". This covers container lifecycle (`make up`/`down`/`restart`/`logs`/`sh`/`rebuild`) just as much as PHP/console commands (migrations, tests, seeding, RBAC, etc.) — see the block below and `make help` for the full list. Only fall back to a raw `docker compose`/`docker compose exec web` invocation when no target covers the case; if that becomes a recurring need, add a `Makefile` target for it instead of repeating the full command.

All PHP/console commands run inside the `web` container:

```bash
# First-time setup
./init.sh          # creates .env from .env.example (does NOT install dependencies)
./setup.sh         # starts Docker, composer install, creates main + test DBs, runs migrations on both

# Docker Compose lifecycle (web + cron + worker + db)
make up / down / restart / logs      # start/stop/restart the stack, follow logs
make sh                              # interactive shell into the web container (TTY)
make rebuild                         # rebuild the image and (re)start web, cron, worker

# Migrations (two DBs: main and test — keep both migrated)
make migrate                        # both DBs
make migrate-main                   # main only
make migrate-test                   # test only

# Generate migrations from existing DB schema (bizley/yii2-migration)
make migration-create table=<table>   # or table='*' for all
make migration-update table=<table>   # diff against migration history

# Seed data
make seed                # optional count=N arg, default 10
make seed-clear

# RBAC bootstrap / token housekeeping
make rbac-assign role=<name> email=<email>   # assign a role (bootstrap the first super_admin)
make refresh-token-prune                     # hard-delete fully-expired refresh tokens

# Tests (Codeception, run against TEST_DB_NAME via config/test.php)
make test                                            # all
make test-functional
make test-unit
make test-one suite=functional class=UsersCest                 # one class
make test-one suite=functional class=UsersCest:testMethodName  # one test
make build                # after changing Codeception modules

# Coverage (pcov; 100% gate enforced by tests/bin/coverage-check.php)
make coverage             # run the suite with coverage and enforce the gate
make coverage-html        # the same, then print the HTML report path

# Code style (PSR-12, PHP CS Fixer)
make cs-check             # dry-run, shows violations/diff
make cs-fix               # auto-fix

# Static analysis (PHPStan, level 5, config in phpstan.neon.dist)
make stan
```

The `Makefile` wraps `docker compose exec -T web ...` (see `make sh` for an interactive shell into the container, which keeps a TTY). Adding a new recurring command should get a `Makefile` target rather than being typed out in full each time. The queue commands (`yii queue/run`, `yii queue/listen`) have **no** `make` target — the long-running `worker` compose service runs `queue/listen` directly (see **Background jobs (queue)**).

App is served at http://localhost:8084, phpMyAdmin at http://localhost:8085, MySQL exposed on host port 3307. DB credentials come from `.env` (read via `getenv()` in `config/db.php` / `config/test_db.php`).

## Architecture

Layered flow for every endpoint: **Controller → Form Request → Service → Repository → ActiveRecord model**, with interfaces in `models/contract/` defining the service and repository shapes.

- `controllers/basic/ApiController.php` — abstract base extending `yii\rest\ActiveController`. It sets up CORS/JSON + JWT bearer auth (shared `controllers/basic/ApiControllerTrait.php`), replaces the default REST actions with its own generic `actionIndex/View/Create/Update/Delete` implementations that delegate to the constructor-injected `$service` (an `ApiServiceInterface`) and gate every action through the injected `AccessControlInterface` `$access` (see **Authorization (RBAC)**). Concrete controllers set `$modelClass`, implement the create/update/search forms, and implement `accessResource()` (the permission-name prefix, e.g. `'album'`). They override `requireCollectionAccess()`/`requireMemberAccess()` when their permissions don't follow the `<resource>.<action>[.any]` naming (e.g. `RolesController`), and `assertVisible()` for resource-specific visibility (a soft-deleted album is a 404 outside the review audience — `AlbumsController`/`PhotosController` via `AlbumVisibilityTrait`). Override an action only when the response differs (e.g. `AlbumsController::actionView` returns an `AlbumViewResponse` DTO).
  - **`?expand=` is deliberately not supported.** Yii's `rest\Serializer` would otherwise resolve `expand` from the query string against the model's `extraFields()`, making *any* relation listed there reachable on an index action — including one gated by a permission that action doesn't require (`permissions` on `GET /roles` needs `role.view`, which `role.index` alone doesn't grant). `ApiSerializer::getRequestedFields()` drops the requested expand list unconditionally, so the param is a silent no-op everywhere and relations are embedded only by the endpoint that owns them (`ApiController::actionView()` / `UsersController::actionMe()` pass `extraFields()` to `toArray()` themselves — that's the one remaining consumer of `extraFields()`). Don't reintroduce client-driven expansion; add the relation to the specific response instead.
- `PhotosController` — photos are a **child resource of albums**, so listing and creation are nested (`GET|POST /albums/<albumId>/photos`) while member actions stay flat (`GET|PUT|DELETE /photos/<id>`); there is deliberately no flat `/photos` listing. It overrides `actionIndex(int $albumId)` (reuses `handleIndex()` but pins the album scope via `PhotoService::getByAlbum($albumId, $criteria)`) and `actionCreate(int $albumId)` (grabs the uploaded file via `UploadedFile::getInstanceByName('file')`, then reuses `handleWrite()` with `PhotoService::createInAlbum()`); `view`/`update`/`delete` use the generic base actions. `PhotoService` implements `PhotoServiceInterface` (extends `ApiServiceInterface`) and additionally depends on `AlbumRepository` (to 404 on a missing album) and the `ImageStorage` component. There is **no `photo.index.any`/`photo.create.any` permission gate on the collection actions** — the catalog has no `photo.index.any`; instead `actionIndex`/`actionCreate` call `findAlbumOrFail()` + `requireVisibleAlbum()` + `access->requireOn('photo.view'|'photo.create', $album)`, so the **album's** ownership/`.any` grants list/upload access. This is the one collection action gated by ownership rather than `requireCollectionAccess()`.
- `models/service/` — `readonly` classes implementing `ApiServiceInterface`; business logic and `NotFoundHttpException` on missing records. Validation failures are returned as the model with errors; the base controller converts them to a 422.
- `models/repository/` — all DB access (queries, batch inserts for seeding). **Every repository has its own contract in `models/contract/repository/`** — `Album`/`Photo`/`User`/`RoleRepositoryInterface` extend the generic `ApiRepositoryInterface` with only the extra methods their consumers actually call, while `Permission`/`RefreshTokenRepositoryInterface` stand alone (neither is a REST collection). Nothing outside `config/di.php` type-hints a concrete repository: the container binds each interface, so services autowire and none of them needs `Instance::of()` wiring or a down-cast to reach resource-specific bulk methods. Declare a new method on the interface only when a consumer needs it. `getAllDP(?SearchCriteria)` builds the `ActiveDataProvider` (default pageSize 20) from the criteria: forced `scope` conditions via `andWhere`, user `filters` via `andFilterWhere` (empty operands skipped), `orderBy`, and page size. Sorting is resolved by the search form, so the provider's own `Sort` is disabled (`'sort' => false`).
- `models/form/` — form requests extending `basic/ApiForm` (a `yii\base\Model`); validate raw request data in the controller before anything reaches the service. Two flavours:
  - **Write forms** (`*CreateForm`/`*UpdateForm` over an abstract per-resource base): validate body params. Create adds `required`; Update is all-optional (partial updates). Only `validatedData()` (attributes actually present in the request) is passed on, so clients can't set server-managed fields (`auth_key`, `access_token`, `password_hash` — clients send plain `password`, hashed in `UserService`). Album ownership is also server-managed: `AlbumForm` deliberately omits `user_id`, so `AlbumsController::actionCreate` forces it to `Yii::$app->user->id` (the album belongs to the authenticated caller) and update can never reassign it. Concrete controllers implement `createForm()`/`updateForm()`.
  - **Search forms** (`*SearchForm` extending `basic/SearchForm`): validate the *query* params of index endpoints (`sort`, `per_page` ≤ 100, plus one attribute per filter) and produce a `SearchCriteria` DTO. Each resource declares `sortableAttributes()` (whitelist — an unknown `sort` field 422s) and `likeAttributes()`/`exactAttributes()` for filtering; a `-` prefix means descending. Concrete controllers implement `searchForm()`. The base `ApiController::actionIndex` runs the shared `handleIndex()` (validate query params → criteria → `service->getAll($criteria)`); `PhotosController` overrides it to pin the album scope via `PhotoService::getByAlbum($albumId, $criteria)`.
- `models/db/` — ActiveRecord models: `User`, `Album`, `Photo`, plus `Role`, `Permission`, `RefreshToken`, `QueueJob` for the RBAC/auth/queue subsystems below. `Photo::$source` (`'seed'` | `'photo'`) records where a file lives so `Photo::getUrl()` can build the right link; the URL logic itself lives in `components/PhotoUrlBuilder` (single source of truth, used by the model and by tests — never hand-concatenate a photo URL). `fields()` on each AR model is where the public API shape is decided and does not mirror the table: `Album::fields()` omits `user_id`/timestamps and casts `is_deleted` to bool; `User::fields()` exposes only `id/first_name/last_name/email`; `User::getAlbums()` filters out soft-deleted albums at the relation level.
- `models/dto/` — readonly DTOs: `BasicResponse`, `PaginationMeta`, `TokenResponse`, `HealthCheckResult`, `AlbumViewResponse` (response shapes with `fromModel()`/`toArray()`), plus `SearchCriteria` (the resolved list-query spec passed from search form → service → repository).
- `models/service/basic/BaseCrudService` / `models/repository/basic/BaseRepository` — the shared CRUD/query plumbing every resource's service/repository extends. `BaseCrudService::saveValidated()` is the single place an invalid model is returned with its errors and never persisted. `BaseRepository::getAllDP()` sets `'validatePage' => false` on pagination — an out-of-range `page` returns an **empty** page rather than clamping to the last one — and exposes `viewRelations()` (eager-load hook for `findById()`) and `batchInsertRows()`. `deleteInBatches()` removes rows in 500-row chunks so locks stay short; it is deliberately **not atomic** — callers must tolerate a partial delete on failure (used to purge an album's photos before the album row itself, see `AlbumService::purgeAlbums()`).

**Photo uploads**: `POST /albums/<id>/photos` is `multipart/form-data` with `title` + `file`. `models/form/PhotoCreateForm` accepts only `jpg, jpeg, png, webp, gif, avif` (extension whitelist; `checkExtensionByMimeType` off) and requires an actual uploaded file. Uploads pass through **two separate seams**, one for encoding and one for storage. `models/contract/image/ImageEncoderInterface` (`encode()` + `extension()`) turns the file into storable bytes; the default `components/image/ImagickWebpEncoder` produces **WebP quality 80** scaled to fit **500×500** preserving aspect ratio (never upscaled), and validates the real content — a non-image that passed the extension check throws here and becomes a 422. **The interface names no imaging library and the encoder takes no constructor defaults**: the three numbers are a published API contract (`config/openapi.yaml`), so they live in `config/params.php` as `photo_max_width`/`photo_max_height`/`photo_quality` and a missing binding fails loudly instead of silently restoring magic numbers. **That rule is general, not encoder-specific**: a parameter fed from `config/` declares no default anywhere in the app (`JwtService::$ttl` — an uninitialised typed property plus an `init()` guard, since a `yii\base\Component` is configured by array — and `RefreshTokenService::$ttl`), and `tests/unit/ConfigDrivenDefaultsTest.php` is the one place that pins it. A new config-driven parameter belongs in that test rather than in a fourth copy of the same assertion. An implementation **must** translate its library's native failure into `yii\base\Exception` — `PhotoService` keys its 422 path off that type, so an untranslated error would surface as a 500.
`components/ImageStorage` composes the two: it asks the encoder for bytes, names the file (`<random>.<extension()>` — no hard-coded `.webp`), and writes it through an injected **`League\Flysystem\FilesystemOperator`** (bound in `config/di.php` to a `LocalFilesystemAdapter` rooted at the `photo_upload_path` param, read from the live app params so an environment can override it; swap for `AwsS3V3Adapter` to move storage to S3 with no code change — `league/flysystem-aws-s3-v3` is installed). Files are keyed `<albumId>/<fileName>`. It touches neither an imaging library nor a disk directly, which is why its tests need no Imagick and no real image bytes. `PhotoService` sets `source = 'photo'`, and cleans up the file on failed validation or on delete. `PhotoUpdateForm` allows changing **only the title** — the album and the stored file are immutable. Seeded photos use `source = 'seed'` and resolve to `web/default-images/`. `config/test.php` overrides the `FilesystemOperator` binding to a `@runtime`-rooted local adapter so test uploads never touch the web root. The web server must be able to write `web/uploads` (`setup.sh` chmods it 777).

**Background jobs (queue)**: slow, retriable side-effects go through a small queue seam — `models/contract/queue/QueueInterface` (`push(JobInterface)`) plus a **command/handler split**: `JobInterface` (`handlerClass()`) is a plain serializable message carrying only data, and `JobHandlerInterface` (`handle(JobInterface)`) holds the behaviour and takes its services by constructor injection. Resolving a handler by name is the one lookup that cannot be wired in advance, so it is isolated behind `models/contract/queue/JobRunnerInterface` (`components/queue/ContainerJobRunner`, which takes the `yii\di\Container` **by injection**, not by reading `Yii::$container`). That is the only service-locator call in the app: the drivers depend on the runner, so neither of them touches the container, and both are constructible in a test without mutating global state. Don't put services on a job — put them on its handler. Two drivers in `components/queue/`: `DbQueue` (default, bound in `config/di.php`) persists a serialized job to the `queue_job` table, and `SyncQueue` runs it in-process (bound in `config/test.php` so tests don't need a worker). The long-running **`worker`** compose service runs `commands/QueueController::actionListen` (`yii queue/listen [delay]`, default 3s) — drains continuously (`DbQueue::processPending()` per pass, batch size `DbQueue::DEFAULT_LIMIT`, which `queue/run` also defaults to so the two can't drift), sleeps only when idle, and stops gracefully on SIGTERM/SIGINT; `yii queue/run` drains once for CI/manual use. The signal handling lives behind `models/contract/StopSignalInterface` (production impl `components/PcntlStopSignal`, using `pcntl` from the `base` Docker stage), so the worker loop depends on a boolean question and a test can substitute a fake that stops it after N passes — without that seam the infinite loop would be untestable. A job that throws is retried up to `DbQueue::$maxAttempts` (default 3, logged as a warning each time), then dropped with `Yii::error()` so one poison job can't wedge the queue. Current job: `DeleteAlbumDirectoryJob` + `DeleteAlbumDirectoryHandler` — `AlbumService` enqueues the on-disk cleanup of a permanently-deleted album's upload directory instead of doing it inline. **yiisoft/yii2-queue is deliberately not used**: its current release caps `symfony/process` at `^7` while this project is on `^8` (PHP 8.5); on a mainstream stack it would back the same `QueueInterface`.

**Transactions & concurrency**: multi-row mutations run inside a DB transaction via the injected `models/contract/service/TransactionRunnerInterface` (`components/DbTransactionRunner` wraps `Yii::$app->db->transaction()`; unit tests pass an inline fake, so services stay DB-free). `RoleService` (create/update/delete/assignRoles) and `UserService::delete` (account + owned albums/photos/files) are wrapped. The RBAC last-role-manager invariant is made concurrency-safe by `RoleRepository::lockManageHolders()` — a `SELECT ... FOR UPDATE` on the `user_role` rows granting `role.manage`, taken inside the transaction before the count check, so concurrent mutations serialize instead of both passing the check.

**Authentication (two-token model)**: access tokens are **stateless**, refresh tokens are **stateful**. The split is deliberate — the access token is checked on every request (so it must be cheap = no DB hit), while the refresh token is checked rarely (once per access-token lifetime), which is exactly where we can afford to reintroduce DB state to gain **revocability**.

- **Access token** — every resource endpoint requires `Authorization: Bearer <token>` (`HttpBearerAuth`, attached after the CORS filter in `ApiControllerTrait` with `except => ['options']` so preflights stay public). It is a stateless HS256 JWT issued/validated by `components/JwtService.php` (app component `jwt`; secret/TTL from `JWT_SECRET`/`JWT_TTL` in `config/di.php` — the secret must be ≥ 32 chars, changing `.env` requires recreating the web container). `User::findIdentityByAccessToken()` resolves the user from the token's `sub` claim; nothing is stored in the DB.
- **Refresh token** — an **opaque** high-entropy string (NOT a JWT), managed by `models/service/RefreshTokenService` over `models/repository/RefreshTokenRepository` + the `refresh_token` table. Only the token's **SHA-256 hash** is stored (a DB leak exposes no usable tokens); the raw value is returned to the client once. Each row belongs to a **family** (`family_id` = one login session / device). Config: TTL from `JWT_REFRESH_TTL` (default 30 days) bound in `config/di.php`. The table has a unique index on `token_hash` (the hot lookup) and a `user_id` FK with `ON DELETE CASCADE`, so a deleted user's tokens vanish — which is why refresh needs no separate "user still exists" check.
  - **Rotation + reuse detection** (`RefreshTokenService::consume()`): a refresh token is single-use — exchanging it revokes it and issues a successor **in the same family**. Presenting an already-revoked token means a copy is loose, so the **whole family is revoked** (forces re-login). Revocation is a soft `revoked_at` timestamp (rows are kept so reuse can be detected).

The **auth flow** lives in `AuthController` (all endpoints public, all rate-limited) through `AuthService` / `AuthServiceInterface`. `AuthService` composes `UserService` (account creation), `RefreshTokenService` (refresh lifecycle) and `JwtService` (access tokens); its private `issueTokens()` returns the `TokenResponse` DTO (`access_token` + `refresh_token` + `token_type` + `expires_in`) for login/register/refresh:
- `POST /auth/login` — `LoginForm` → `AuthService::login()` → `UserRepository::findByEmail()`; bad credentials → 401. Starts a new token family.
- `POST /auth/register` — public self-registration (closes the chicken-and-egg loop: no token needed to get an account). Reuses `UserCreateForm` and delegates creation to `UserService::create()` (password hashing / server-managed fields stay in one place), then logs the user straight in → 201; duplicate email / missing field → 422. `AuthService::register()` returns `User|TokenResponse`.
- `POST /auth/refresh` — `RefreshTokenForm` (`refresh_token` required) → `AuthService::refresh()` → `RefreshTokenService::consume()`, issuing a **fresh pair** in the same family; unknown/expired/revoked token → 401.
- `POST /auth/logout` — revokes the presented token's **family** (log out this device). Best-effort and idempotent: unknown token → still 204, no info leak.
- `POST /auth/logout-all` — revokes **every** family of the token's owner (log out all devices). Both logout endpoints share `RefreshTokenForm` and return **204**.

Email uniqueness is validated at the form level: `UserCreateForm` does a plain unique check, `UserUpdateForm` gets the record id via constructor (`updateForm(int $id)`) and excludes it from the check.

**Authorization (RBAC)**: flat, no role hierarchy or inheritance. A role is a named set of permissions; a user may hold **several** roles and their effective permissions are the **union**. There is no `user` role — a freshly registered account has **no roles** (a "base user"); roles are an upgrade on top of the base abilities. Storage is four own tables (not `yii\rbac`): `permission` (catalog), `role` (`is_system` protects the three seeded roles), `role_permission`, `user_role` (all links cascade on delete). Two migrations seed it: `m260711_000000` (tables) and `m260711_000001` (catalog + `moderator`/`admin`/`super_admin`).

- **Permissions** are code-checked strings, so they live **only in migrations** (their lifecycle is the code's) — there is no create/update/delete for them, only `GET /permissions` (needs `permission.index`) for the role-composition UI. Catalog permissions are all `.any`-scoped "upgrades" (e.g. `album.update.any`, `photo.delete.any`, `user.index.any`, `role.manage`, `role.assign`). Every new migration that adds a permission **must also grant it to `super_admin`** (defined as "holds every permission") — this is no longer a matter of remembering: `PermissionContractTest` fails the build when the catalog and super_admin's grants disagree. Each operation in `config/openapi.yaml` also declares the catalog permissions that grant it, in the `x-permission` extension (an empty list for a public or base-ability endpoint), plus `x-permission-ownership: true` where owning the subject grants it as well. `x-` keys are ignored by Swagger UI and by every OpenAPI validator, so this costs the rendered docs nothing and makes the RBAC model machine-checkable.
- **`models/service/AccessControlService`** (`AccessControlInterface`, memoized per request, injected everywhere via DI) answers the two questions controllers ask: `can('user.index.any')` (global) and `canOn('album.update', $model)` (per-record). `canOn` allows the action when a role grants the `.any` variant **or** the caller **owns** the subject and the ability is one of the implicit `OWN_ABILITIES` (own album/photo/profile — this is what a base user gets without any role; ownership is resolved polymorphically via `models/contract/OwnableInterface::getOwnerId()`, which `Album`/`Photo`/`User` implement — no `instanceof` switch in the service). Deliberately *not* ownership-granted: `user.view`/`user.delete` and all `*.index` gated through `ApiController::requireCollectionAccess()` — the one exception is the photo collection actions, which are gated by **album** ownership instead (see the `PhotosController` bullet above). Because each action checks **only its own** permission, a custom role of just `photo.delete.any` can delete any photo without being able to view it. Denial → `ForbiddenHttpException` (403); `/users/me` and `/users/me/permissions` are the only never-gated endpoints (any authenticated user, so an exotic role can still ask "who am I / what may I do" for the client to build its UI).
- **The three system roles**: `moderator` (see all users; manage all albums but delete only via **soft-delete**; full photo access incl. permanent delete), `admin` (full user CRUD, permanent album delete + restore, `role.index`/`role.assign`), `super_admin` (everything, incl. `role.manage`).
- **Role API** (`RolesController` + `RoleService`/`RoleServiceInterface`): `GET /roles` (`role.index`, name+description), `GET /roles/<id>` (`role.view`, +permissions), and create/update/delete (`role.manage`, super-admin only) composing a role from catalog permissions (unknown name → 422; system roles can be re-composed but not renamed/deleted → 422/409). Assignment is a child resource of users: `GET|PUT /users/<id>/roles` (`role.assign`; PUT is a full replacement, empty array revokes all). Two safety rules in `RoleService`: **anti-escalation** (a holder of `role.assign` without `role.manage` cannot grant/revoke any role carrying `role.manage`/`role.assign` — so an admin can't mint or demote admins) and the **last-role-manager invariant** (no operation — role delete/re-compose, assignment change, user delete — may leave the system with zero holders of `role.manage`; violation → 409). The same guards protect user mutation: an admin can't update/delete a `role.manage` holder's account, and the last super admin can't delete themselves.
- **Pseudo-deletion of albums** (`album.is_deleted` + optional `album.delete_reason`): `DELETE /albums/<id>` has one route, outcome by permission — permanent for whoever may delete outright (the owner, or `album.delete.any`; permanent wins if a role has both), soft (flag + optional `reason`, idempotent) for `album.soft-delete.any` only. Soft-deleted albums are hidden from every listing by default (`AlbumSearchForm`'s `is_deleted` filter / `?is_deleted=1` surfaces the review queue for `album.index.any`) and are a 404 for their owner until an admin `POST /albums/<id>/restore` (`album.restore`). The review audience (`album.view.any`/`photo.view.any`) still sees them.
- **First super admin**: everything RBAC-driven needs an existing `role.manage` holder, so bootstrap from the console — `make rbac-assign role=super_admin email=<email>` (`RbacController::actionAssign`, idempotent). Registration/user-creation assign **no** role.

**Login rate limiting (brute-force protection)**: `components/RateLimiter.php` is a cache-backed `ActionFilter` attached in `AuthController::behaviors()` that throttles the auth endpoints per client IP, with an **independent counter per action** (the cache key includes `$action->getUniqueId()`, so login/register/refresh/logout don't share a budget) — max attempts / window configured once in `config/di.php` from `LOGIN_RATE_LIMIT_ATTEMPTS`/`LOGIN_RATE_LIMIT_WINDOW` env vars (defaults 5 / 60s). Every non-OPTIONS request increments the counter and refreshes the window; exceeding the limit → 429 with a `Retry-After` header; a response < 400 (a success) resets the counter, while failures (401 thrown, 422 set) do not. It uses the `cache` app component (FileCache; `config/test.php` points it at `@runtime/test-cache`, and `BaseCest::_before` flushes it so counters don't leak between tests).

**Health check**: `GET /health` (`HealthController`, public, unauthenticated, no rate limiting — plain `yii\rest\Controller` + `ApiControllerTrait` like `AuthController`) calls `HealthService::check()` (`HealthServiceInterface`), which runs `SELECT 1` against the injected `yii\db\Connection` and returns a `HealthCheckResult` DTO (`{"status": "ok"|"error", "checks": {"database": ...}}`). Since `db` is an app *component* rather than a container-managed class, it can't be wired with `Instance::of()` (that only resolves classes/definitions known to the container) — `config/di.php` binds `HealthService::class` to a closure that pulls `Yii::$app->db` directly. 200 when healthy, 503 otherwise.

**API documentation (OpenAPI/Swagger)**: `config/openapi.yaml` (OpenAPI 3.0) is the **single source of truth** for the API's request/response shapes and RBAC gates — keep it in sync whenever an endpoint changes (there is no generated-from-code spec). The YAML is written by hand, but it is **not taken on trust**: the contract gates in `tests/unit/contract/` hold the code to it (see **The contract gates** below), so a spec that drifts from the code fails the build rather than quietly misleading a client. `DocsController` serves it publicly at `GET /docs` (Swagger UI, HTML loaded from a pinned `swagger-ui-dist` CDN) and `GET /docs/openapi.yaml` (raw spec, 404 when the file is missing). The spec's location is the `openapi_path` param (`config/params.php`) rather than a hard-coded alias, so it is configurable per environment and the missing-file branch is testable. It extends plain `yii\web\Controller` (not the `ApiController`/REST stack) and sets `Response::FORMAT_RAW` per action, so the docs deliberately bypass the JSON envelope and JWT auth. Routes are the first two explicit rules in `config/url_rules.php`. This replaced the old hand-written `docs/api/API.md`.

**Unified response format**: every response is `{"success": bool, "data": ..., "code": int}`, built by `models/dto/BasicResponse`. A `DataProviderInterface` result (any index action) is serialized to `data.items` + `data.pagination` via `models/dto/PaginationMeta`; an error (`≥400` status) puts `{"message": ..., "error": {...}}` **inside** `data` via `BasicResponse::error()` — so form/model validation errors surface at `data.error`, not at the top level. This is enforced in two places — `components/ApiSerializer.php` (wraps normal REST responses, converts ≥400 statuses to the error shape) and `components/JsonErrorHandler.php` (renders uncaught exceptions in the same shape, with file/line/trace only when `YII_DEBUG`). New endpoints get this automatically; don't hand-build response envelopes.

**Routing**: the shared rule table lives in `config/url_rules.php` (required by **both** `web.php` and `test.php`, which keep only their own `urlManager` flags like `enableStrictParsing`; `test.php` also overrides the `FilesystemOperator` DI binding to `@runtime` so test uploads never touch the web root — see the Photo uploads paragraph above). A `yii\rest\UrlRule` with `pluralize => false` covers `users`, `albums`, `roles`; a `photos` `UrlRule` with `except => ['index', 'create']` leaves only `/photos/<id>` (view/update/delete) — no flat collection (`GET /photos` → 405). Everything else is an explicit rule declared **before** those UrlRules so it wins: photos nested under their album (`GET|POST albums/<albumId>/photos`), the current-user endpoints (`GET users/me`, `GET users/me/permissions` → `users/me`, `users/me-permissions`), role assignment as a child of users (`GET|PUT users/<id>/roles`), `albums/my`, `POST albums/<id>/restore`, and the read-only `GET permissions`. Adding a resource means: migration, AR model, repository + service (with contracts), create/update/search form requests, a controller extending `ApiController` that implements `accessResource()`, seeding its permissions in a migration (and granting them to `super_admin`), and adding the controller to `config/url_rules.php`.

**Console commands** live in `commands/` (namespace `app\commands`), extend `basic/BasicConsoleController` (prints elapsed execution time after each action), and use the same constructor DI pattern as web controllers. `config/console.php` maps `migrate`, `migrate-test` (same `migrations/` path, different DB component), and `migration-creator`; other controllers are auto-discovered from the namespace (`SeederController` → `seeder`, `RefreshTokenController` → `refresh-token`, `RbacController` → `rbac`). `rbac/assign <role> <email>` (`make rbac-assign role=… email=…`) appoints the first super admin (idempotent) — see **Authorization (RBAC)**. `refresh-token/prune` (`make refresh-token-prune`) hard-deletes fully-expired `refresh_token` rows — expired tokens can't be exchanged and aren't needed for reuse detection, so it's meant to run on a cron to keep the table bounded (still-valid revoked rows are kept).

## The contract gates — `config/openapi.yaml` is checked, not trusted

`tests/unit/contract/` holds six gates that answer one question the rest of the suite cannot: **does the code do what the published document promises?** They live in a subdirectory of the *unit* suite rather than in a suite of their own — Codeception's loader recurses, so they need no configuration, and every gate needs a booted application anyway (`Yii::$app->urlManager`, the `permission` table, `Yii::$app->params`), which `tests/unit.suite.yml`'s `Yii2` module already provides. `make test-contract` runs only these; `make coverage` must stay a bare `codecept run` (coverage is merged across suites at the end of one process).

- `RouteContractTest` — every route the application answers is documented, every documented operation is **actually routable**, and every documented route targets a real action. The second direction runs the real `UrlManager` rather than a second set difference, because that is the only way to catch *shadowing* (`GET albums/my` is declared before the `albums` REST rule; swap them and every set comparison stays green while `/albums/my` resolves to `albums/view`).
- `ResponseSchemaContractTest` — each response schema's property set equals the `fields()`/`toArray()` that produces it, **and every schema is either mirrored or listed in `NOT_MIRRORED` with a written reason**. That census is the load-bearing assertion: without it the mirrors are a snapshot of whichever schemas someone happened to think of.
- `SearchFormContractTest` — each `*SearchForm`'s sortable whitelist and like/exact filters equal what the index operation documents, plus "no documented query parameter is left unclaimed", and the shared `MAX_PAGE_SIZE`/`PAGE_SIZE` bounds.
- `WriteFormContractTest` — each request schema's attributes, `required` list and length limits equal the form request that validates it. Limits are **probed at the boundary in both directions** with an otherwise-valid value, so a form that simply dropped its length rule cannot pass.
- `PermissionContractTest` — the catalog (read from the test DB, i.e. the migration's *effect*), the `x-permission` extensions and the permission literals in the code all describe the same model; super_admin holds everything; and a bridge asserts each generically gated operation declares the permission its controller actually composes.
- `SpecIntegrityContractTest` — the document parses, every `$ref` resolves, every operation declares a response. This is the external OpenAPI linter's job, done in-toolchain so a PHP image needs no Node.

Shared readers live in `tests/_support/`: `OpenApiSpec` (parsed once per run, path from `params['openapi_path']` so it reads the file `DocsController` serves), `RouteTable` (expansion via Yii's own `UrlManager`, so `except`/`{id}`/the seven default REST patterns cannot drift from Yii), and `ContractTestCase`. They must be there and not beside the gates: Codeception autoloads only `_support/`, and the suite loader's `~Test\.php$~` pattern would never load a `*TestCase.php` under `tests/unit/contract/`.

Four standing rules:

- **Every gate is a set difference against an explicit registry plus an explicit, commented skip list** — never a spot check. Add a schema, an operation, a form or a permission and the build stays red until it has been *placed*.
- **Always both directions.** "Documented but not implemented" is as much a defect as "implemented but not documented".
- **Where the document carries something only in prose** — a resource's sortable attributes, the accepted upload extensions, the 500×500/quality-80 numbers — the gate parses that prose rather than keeping a transcribed copy. That is what stops the sentence a human reads from drifting away from the code, and every such regex is paired with an "it matched at all" assertion so a reword fails instead of comparing nothing. Data-driven loops carry the same guard (`assertGreaterThan(0, $checked)`).
- **A contract test asserts a shape, never a behaviour.** If deleting `tests/unit/contract/` would drop line coverage, the missing test is behavioural and belongs in `tests/unit/` or `tests/functional/` — a structural gate must never be the sole coverer of a line. `@covers`/`#[CoversClass]` remain forbidden here, and these files are the strongest temptation to add one.

Because the gates are green on a tree that already agrees, **prove a new gate bites by mutation**: break one thing (delete a route, rename a field, drop a sortable attribute, mis-declare an `x-permission`), confirm the failure names the culprit, restore. Record it in the PR.

## Testing Conventions

- Functional tests (`tests/functional/`) extend `BaseCest`, hit real endpoints via REST module, and insert fixtures with `$this->insertRecord('table', [...])` against the test DB. `tests/functional.suite.yml` sets the Yii2 module's `transaction: false` (REST requests run through a real HTTP-like cycle, incompatible with wrapping each test in a rolled-back transaction) — this is *why* `BaseCest::_before` must truncate tables itself instead of relying on transaction rollback. `_before` truncates tables (and deletes non-system roles, keeping the migration-seeded catalog/roles as reference data), then creates an auth user (`$this->authUserId`, email `auth.user@example.com`) with the **`super_admin`** role and sets a Bearer token for every request — so the shared CRUD tests aren't blocked by RBAC; user-list pagination totals include this user. RBAC helpers: `actingAsUserWithRole($I, $role, $overrides)` inserts a fresh user (pass `null` for a roleless base user) and authenticates as them; `assignRole()`/`insertRole($name, $permissions)`/`roleId()` manage roles; `sendPutJson($I, $url, $body)` PUTs a JSON body (needed when the body carries a possibly-empty array — form encoding drops empty arrays, so `config/test.php` also registers the JSON parser like production). Call `$I->deleteHeader('Authorization')` to test unauthenticated behavior (see `AuthCest`).
- Unit tests (`tests/unit/`) extend **`tests\_support\BaseUnitTest`** (namespace `tests\unit`) — **every one of them**, so a helper added to the base is visible everywhere — and test a class in isolation with PHPUnit mocks of its collaborators; no DB (except rules that query during `validate()`, e.g. `User`'s `unique` email and `Photo`'s `album_id` `exist`, and the few repository tests that exist precisely to hit it). `BaseUnitTest` provides `immediateTx()` (a `TransactionRunnerInterface` stub that runs the operation without a real transaction) and `persistUser()` (a user fixture removed automatically in teardown — the unit mirror of `BaseCest::insertUser()`). Put any other helper two unit tests both need on that base rather than copying it.
- **Three shared traits in `tests/_support/` serve both suites** (Codeception autoloads that directory by basename, which is why files there can declare any namespace — and why the contract gates' `OpenApiSpec`/`RouteTable`/`ContractTestCase` live there too). Use them rather than re-solving these problems per test:
  - `CapturesConsoleOutput` — mixed into an anonymous subclass of a console controller. Their `stdout()`/`stderr()` write straight to the STDOUT stream, which `ob_start()` **cannot** capture, so overriding is the only option; the trait records the lines so a unit test can assert on them (`assertStringContainsString(..., implode('', $c->consoleOut))`) and a Cest can ignore them.
  - `CreatesImageFixtures` — `imageFixture()`, `detailedImageFixture()` (noisy, for anything asserting on encoded size — a flat colour compresses the same at any quality), `animatedGifFixture()`, `notAnImageFixture()`. Paths are unique per call and deleted automatically.
  - `RestoresGlobalState` — `swapBinding()` / `overrideParam()`. **Any test that mutates `Yii::$container` or `Yii::$app->params` must go through these**, never `Yii::$container->set()` directly: they record what was bound *in this run* and restore it, which matters because `config/test.php` overrides some of `config/di.php`'s bindings — restoring "what di.php says" would put the production filesystem into a test run.
- Both base classes wire the traits into their teardown (`BaseUnitTest::tearDown()`, `BaseCest::_after()`), so **no Cest should override `_after()`** — a forgotten `parent::_after()` would leak a stub into every later test.
- `PhotosCest` uploads with `$I->sendPost($url, ['title' => ...], ['file' => $path])` and generates image fixtures on the fly with Imagick; it asserts the stored file is WebP and correctly resized. Photo fixtures inserted directly need a `source` value (`'seed'`/`'photo'`). `ImagickWebpEncoderTest` likewise runs against a real Imagick — that class exists to produce specific bytes, so a mocked imaging library would assert nothing; it also pins that the bounding box and quality are *read from the object*, which is what catches the `params.php` → `di.php` wiring going dead. `ImageStorageTest`, by contrast, uses a fake encoder and touches no filesystem at all — if a test of storage needs Imagick, the seam has been broken.
- A test that rebinds something in `Yii::$container` or `Yii::$app->params` **must restore it** (`HealthCest`, `AuthCest`, `DocsCest` all do this in `_after`), otherwise the stub leaks into every later test in the run. `AuthCest::_after` restores from `config/di.php` itself so the canonical definition isn't duplicated in the test.
- `config/test.php` binds `QueueInterface` to `SyncQueue` so jobs run inline. That is also what makes job handlers *coverable* — under `DbQueue` they would execute in the worker process, invisible to coverage. Don't switch tests to `DbQueue`.
- `config/test.php` uses strict URL parsing and disables CSRF; test DB config is `config/test_db.php`.
- There is no acceptance suite; the Yii2-template leftovers (`tests/acceptance/`, `AcceptanceTester.php`, `acceptance.suite.yml.example`) have been removed. Don't reintroduce them without a suite that actually runs.

## CI/CD & Static Analysis

**CI** — `.github/workflows/ci.yml` runs on every push and pull request: `composer install`, then four gates — PHP CS Fixer (`--dry-run`), PHPStan, the full Codeception suite against a MySQL 8 service, and the **100% coverage gate** (`tests/bin/coverage-check.php`). It runs natively on the runner (PHP 8.5 + Imagick + pcov via `shivammathur/setup-php`), not through Docker; DB/JWT/rate-limit config is passed as workflow `env:` (the same vars the app reads via `getenv()`), and only the test DB is migrated (`migrate-test/up`). The test step runs *with* coverage rather than alongside a plain run — the pass/fail signal is identical and a second full run would only double the wall clock — and pins `pcov.directory`/`pcov.exclude` on the command line because `setup-php` leaves the former at `auto`. On a red gate the HTML report is uploaded as a build artifact. Keep the CI steps in sync with the `Makefile` targets (`cs-check`, `stan`, `test`, `coverage`) — they must stay runnable both ways.

**CD** — `.github/workflows/cd.yml` is chained to CI via `workflow_run` (triggers only after the **CI** workflow completes on `master`), so a red CI never deploys (and its badge stays neutral rather than red) — but the two jobs enforce that differently: `build-image` carries the explicit `if: github.event.workflow_run.conclusion == 'success'` guard, while `deploy` has no `if` of its own and is gated only indirectly via `needs: build-image` (a skipped or failed `build-image` skips `deploy` too). It has two jobs: `build-image` builds the `prod` stage of the multi-stage `Dockerfile` (`target: prod` — `composer install --no-dev --no-scripts` + baked app code, on top of the shared `base` stage) with buildx + GHA layer cache, then smoke-tests it (`php --version` inside the image); `deploy` runs through a `production` GitHub Environment so it shows in the repo's Environments/Deployments tab, but the actual release is **simulated** (echoed steps) — this sample deliberately provisions no real server. The image is built with `push: false`/`load: true` (never pushed to a registry). The `prod` stage uses `--no-scripts` so Yii's `postInstall` (cookie-key generation) is skipped — `COOKIE_VALIDATION_KEY` comes from env at runtime instead — and only `yiisoft/yii2-composer` is in `allow-plugins`. Dev and prod share the `base` stage, so there is no runtime setup to keep in sync between compose and the image.

PHPStan config is `phpstan.neon.dist` (level 5, scans `commands`/`components`/`config`/`controllers`/`models`). Two non-obvious settings make it green without false positives: `bootstrapFiles` + `scanFiles` both point at `vendor/yiisoft/yii2/Yii.php` so the global `Yii` class (a generic subclass of `BaseYii`) is both executed for its constants and reflected for its inherited static methods (`Yii::getAlias()` etc.); and `dynamicConstantNames` lists `YII_DEBUG`/`YII_ENV*` because `BaseYii` defines them as `false`/`'prod'` defaults, so without this PHPStan reports every `if (YII_DEBUG)` branch as dead code. PHPStan needs `--memory-limit=512M` (the web container's PHP caps at 128M). Fix real type errors rather than lowering the level or adding ignores.
